# ToddlerBox 0.5.3 — release preparation

Unpublished candidate, sequence 6 (after signed 0.5.2 sequence 5). No production
signature, tag or stable-channel advancement is implied by this guide. Preserve
published artifacts and accepted rollback; do not run older publish workflows
with their hardcoded 0.4.0 or 0.5.2 release identities.

## App/system update

- Shared GPU-first presentation with one bounded early software startup fallback.
- Paint input/redraw hardening; optional bounded diagnostic timing stays off by
  default. Intermittent drawing lag remains tracked in #29. Stopped/dotted strokes
  are considered resolved by maintainer retesting; reopen if they recur.
- Math visible numeral speech with silent revelation and passive objects.
- Reading/Math bounded chronological Back/Next history, restoring exact states.
- Corrected, licensed and separately credited plum recording.

The fixed update destinations, child-data schema and offline activity model are
unchanged. Keep parent configuration, credentials, identity, sync state and child
work outside releases. App updates do not reinstall Ubuntu, install apt packages
or roll back child data. This HP can continue using the accepted development build
while the exact CI artifacts are qualified.

## Future installer image

Include libinput-tools, evtest, smartmontools and pciutils alongside the existing
audio tools. SMART aliases and SysV startup remain disabled/masked. The installed
root/parent-only diagnostic smoke helper is image-only. The new fresh-image check
compares package additions with a genuine successful earlier image, checks new
unit/cron policy, performs bounded enumeration and retains diagnostics.json.
No child diagnostic UI or background monitoring is introduced.

## Gates before release

1. Freeze source, version and sequence before building. Retain exact ISO, update
   bundle, embedded app archive, package manifest, checksums and build-record.json
   in the dev-installer-candidate workflow artifact. Its initial status is pending;
   it is not qualification evidence by itself.
2. Pass CI and fresh offline disposable-VM installation, including diagnostic
   commands, new package/unit inventory, all activities and independent recovery.
3. Pass signed published-baseline hops and exact-candidate update/accept/rollback/
   reset tests. The current portable chain starts at the published 0.4.0 installer
   and signed 0.5.0/0.5.1. Before publication, also establish the current 0.5.2
   appliance path with the explicitly recovered public trust anchor. Never weaken
   production signature/sequence guards or treat a VM test key as production trust.
4. Record results and exact artifact identities in VALIDATION.md. Reuse evidence
   only for unchanged inputs; do not substitute the host-built local artifact for
   the CI-built bundle, even when runtime code matches.
5. Sign the qualified bytes using the existing root-private production key without
   displaying/copying it. Verify signatures with the shipped public key ring.
6. Parent-initiate Drive backup, install the exact final candidate and perform
   supervised physical checks. Obtain explicit acceptance of that candidate;
   earlier development acceptance does not silently accept replacement bytes.
7. Prepare reviewable publication metadata and obtain final publication approval.
   Verify uploaded bytes and signed stable metadata before advancing the channel.
